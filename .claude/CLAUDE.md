## Client (`client/`)

- `flutter pub get` — install dependencies
- `flutter run` — run on a connected device/simulator (pick one interactively if multiple)
- `flutter run -d chrome` / `flutter run -d macos` — run targeting a specific platform
- `flutter analyze` — static analysis (`analysis_options.yaml`, `flutter_lints`)
- `flutter test` — run unit/widget tests once
- `flutter build web` — production web build (output in `build/web/`, gitignored)

Structure is the Flutter default:
- `lib/main.dart` — app entry point (currently the unmodified `flutter create` counter demo)
- `test/` — tests, mirroring `lib/` (e.g. `lib/foo/bar.dart` → `test/foo/bar_test.dart`)
- `pubspec.yaml` — dependencies and app metadata
- `android/`, `ios/`, `macos/`, `linux/`, `web/` — platform-specific projects generated by `flutter create`

### Development methodology: Spec-Driven Development + TDD

New features go through the **spec-driven** skill (`.claude/skills/spec-driven/SKILL.md`): write a spec in `.claude/specs/<feature-slug>.md` first, then drive implementation with a failing unit test (red) before writing the code that passes it (green). Specs accumulate in `.claude/specs/` as living documentation — see `.claude/specs/_template.md` for the format.

TDD here is enforced by convention (the skill above), not tooling: [`tdd-guard`](https://github.com/nizos/tdd-guard) was evaluated and removed, because it has no official reporter for Dart/Flutter (`flutter test`) — only JS/TS (Vitest, Jest, Storybook), Python (pytest), PHP (PHPUnit), Go, Rust, Ruby (RSpec), .NET, and Java/Kotlin (JUnit5) are supported, with no open issues/PRs for Dart upstream. Without a reporter it has no real test-result signal to block on, so it would only add friction without actually enforcing anything. Revisit this if a community Dart reporter appears, or if writing a custom one (feeding `flutter test`'s JSON output into tdd-guard's expected format) becomes worth the effort.

## Vision

The long-term goal is a personal multi-function agent, controlled primarily by voice through a native client. Planned capabilities beyond the initial phase include controlling local/smart-home products (e.g. SwitchBot) and other integrations, added incrementally as new "skills" behind the same voice interface.

**Phase 1 (current focus):** an English-speaking practice system — the user speaks English, an AI converses with them and helps them practice, via the native client's voice input/output.

## Planned architecture

- **Client:** a native mobile app (Flutter/Dart) responsible for voice input/output and the conversational UI. This is the single entry point end users interact with, and it is expected to grow new screens/features as new agent skills are added, not be replaced by them.
- **Backend:** planned to be a Go service, if/when backend logic is needed beyond calling an AI API directly from the client. When built, it should follow DDD with an onion (hexagonal-style) architecture — domain logic at the core, with adapters at the edges for things like the AI conversation provider, and later, integrations such as SwitchBot. This layering matters because the backend is meant to support multiple, unrelated "skills" (English learning today, smart-home control and others later) without those skills' infrastructure concerns leaking into shared domain logic.
