## Client (`client/`)

Flutter SDK is installed via Homebrew (`brew install --cask flutter`, stable channel). Run all commands from `client/`:

- `flutter pub get` — install dependencies
- `flutter run` — run on a connected device/simulator (pick one interactively if multiple)
- `flutter run -d chrome` / `flutter run -d macos` — run targeting a specific platform
- `flutter analyze` — static analysis (`analysis_options.yaml`, `flutter_lints`)
- `flutter test` — run unit/widget tests once
- `flutter build web` — production web build (output in `build/web/`, gitignored)

Structure is the Flutter default:
- `lib/main.dart` — app entry point (currently the unmodified `flutter create` counter demo)
- `test/` — tests, mirroring `lib/` (e.g. `lib/foo/bar.dart` → `test/foo/bar_test.dart`)
- `pubspec.yaml` — dependencies and app metadata
- `android/`, `ios/`, `macos/`, `linux/`, `web/` — platform-specific projects generated by `flutter create`

Platform status on this machine (`flutter doctor`): macOS desktop and Chrome (web) work out of the box. Android support is off (feature flag `no-enable-android`, no Android SDK installed). iOS has Xcode but CocoaPods isn't installed, so iOS plugins won't build until it is — fine for now since nothing beyond `localhost` web/macOS dev was requested.

### Development methodology: Spec-Driven Development + TDD

New features go through the **spec-driven** skill (`.claude/skills/spec-driven/SKILL.md`): write a spec in `.claude/specs/<feature-slug>.md` first, then drive implementation with a failing unit test (red) before writing the code that passes it (green). Specs accumulate in `.claude/specs/` as living documentation — see `.claude/specs/_template.md` for the format.

TDD here is enforced by convention (the skill above), not tooling: [`tdd-guard`](https://github.com/nizos/tdd-guard) was evaluated and removed, because it has no official reporter for Dart/Flutter (`flutter test`) — only JS/TS (Vitest, Jest, Storybook), Python (pytest), PHP (PHPUnit), Go, Rust, Ruby (RSpec), .NET, and Java/Kotlin (JUnit5) are supported, with no open issues/PRs for Dart upstream. Without a reporter it has no real test-result signal to block on, so it would only add friction without actually enforcing anything. Revisit this if a community Dart reporter appears, or if writing a custom one (feeding `flutter test`'s JSON output into tdd-guard's expected format) becomes worth the effort.

## Vision

The long-term goal is a personal multi-function agent, controlled primarily by voice through a native client. Planned capabilities beyond the initial phase include controlling local/smart-home products (e.g. SwitchBot) and other integrations, added incrementally as new "skills" behind the same voice interface.

**Phase 1 (current focus):** an English-speaking practice system — the user speaks English, an AI converses with them and helps them practice, via the native client's voice input/output.

## Planned architecture

Three principles drive every choice below (design doc §01) — when a decision doesn't obviously follow from them, that's a sign it needs re-checking against the doc:
1. **Hot path vs. cold path.** Real-time conversation gets zero extra latency; pronunciation/grammar analysis runs async after the conversation ends.
2. **Free/local by default.** Anything that doesn't need to be paid or cloud-hosted runs on-device; cloud is reserved for what actually needs it for quality (response generation, and TTS until Kokoro is integrated). STT stays on this on-device/free list too, via `DictationTranscriber` — see the finding below for the (initially wrong) detour that took to confirm.
3. **One swap point.** The cascade (STT+LLM+TTS composed) vs. realtime speech-to-speech choice is hidden behind a single `ConversationSessionPort`-equivalent interface, so the app layer never needs to know which is active.

- **Client (`client/`, Flutter):** no backend server — a serverless hybrid, all business logic in the client. Layering (ports & adapters, not full DDD tactical patterns — see design doc §05/§13 for why those were deliberately skipped):
  - `lib/domain/` — pure Dart, no I/O, unit-testable without a device or simulator. Built so far: `voice_loop_state.dart` (idle/listening/speaking reducer, the walking-skeleton precursor to the real `sessionMachine` — no `thinking`/barge-in yet since there's no LLM to think with). Still target/not built: conversation models (`Session`/`Turn`/`Message` — named generically, not `Lesson`/`LessonTurn`, so phase 2's agent use case doesn't force a rename later), `contextPolicy` (history compression into 3 layers: recent turns raw, periodic on-device summary, user profile), the full `sessionMachine` (idle→listening→thinking→speaking, plus barge-in — this is where most bugs concentrate per the design doc, model it explicitly rather than with boolean flags).
  - `lib/ports/` — abstract interfaces only. Built: `stt_port.dart`, `tts_port.dart`. Still target: `ConversationSessionPort` (the one true swap point), `LlmPort` (carries a `tools` param from day one, always empty in phase 1 — cheap now, expensive to retrofit into a streaming implementation later), `SummarizerPort`, `ConversationRepository`.
  - `lib/adapters/` — concrete implementations. Built (walking skeleton — `.claude/specs/voice-loop-walking-skeleton.md`, verified on-device 2026-09-22): `stt/speech_to_text_stt.dart` (the `speech_to_text` plugin, not yet `DictationTranscriberStt`) and `tts/native_speech_synthesizer_tts.dart` (a custom `AVSpeechSynthesizer` MethodChannel bridge in `ios/Runner/AppDelegate.swift` — not the `flutter_tts` plugin, and not yet Kokoro; see the CocoaPods note below for why). Still target: `session/CascadeSession` (composes Stt+Llm+Tts, phase 1) and, later, `session/RealtimeSession` (speech-to-speech, not built yet — kept swappable, not built ahead of need); `stt/DictationTranscriberStt` (platform channel to `DictationTranscriber`, on-device, free — see the STT finding below for why not `SpeechTranscriber` or Deepgram); `summarizer/FoundationModelsSummarizer` (platform channel to Apple's on-device ~3B model, on-device, free); `llm/...` (cloud, gpt-4.1-mini/gemini-flash class); `tts/...` migrating the walking-skeleton bridge to on-device Kokoro — see below; `repo/...` (local persistence).
  - `lib/app/` — Built: `voice_loop_screen.dart` (the walking-skeleton screen: mic control, phase badge, live/final transcript) + `main.dart` wiring. Still target: the real conversation/review screens.

  **CocoaPods is being avoided project-wide, on the user's explicit instruction — do not suggest installing it.** Flutter is deprecating CocoaPods in favor of Swift Package Manager (`flutter config --enable-swift-package-manager` is enabled in this project); a plugin that ships no `Package.swift` (e.g. `flutter_tts`) forces CocoaPods back into the iOS/macOS build the moment it's added, even with SPM enabled. When a plugin has this problem, prefer a plugin that already supports SPM, or write a small custom platform-channel bridge to the underlying OS framework directly (as done for TTS above) — don't install CocoaPods as the fix. `ios/Podfile` has been deleted and the `Pods` includes removed from `ios/Flutter/{Debug,Release}.xcconfig` accordingly; don't regenerate them.

  Built in the design doc's §12 order so far: voice loop alone (walking skeleton, above) — done. Next: the real `DictationTranscriberStt`/Kokoro bridges, then `CascadeSession`, `sessionMachine`+persistence, the `FoundationModelsSummarizer` bridge, and the review UI.

- **Technology choices** (design doc §03):

  | Area | Choice | Where |
  |---|---|---|
  | STT | `DictationTranscriber` — see the finding below for why not `SpeechTranscriber` (broken) or Deepgram (unnecessary for personal use) | on-device, free |
  | Response generation | gpt-4.1-mini / gemini-flash class | cloud |
  | TTS | cloud today → **Kokoro-82M on-device (adoption confirmed, see below)** | migrating |
  | Summarize/correct | FoundationModels (~3B) | on-device, free |

- **TTS on-device migration — Kokoro-82M, adoption confirmed (design doc §09).** The listening/quality test (implementation step 1 of that section) passed: see `investigation_docs/kokoro_tts_listening_test.ipynb` — a 10-point checklist (vowel/consonant accuracy, stress placement, question intonation, phrase breaks, contractions, numbers/abbreviations, speed changes, short-response naturalness, listening fatigue, A/B vs. cloud TTS) all passed, so Kokoro is judged acceptable as a pronunciation model for learners. The G2P licensing risk (`espeak-ng`, GPLv3) that the design doc originally flagged as the biggest risk is resolved: `MisakiSwift` (Apache-2.0) provides the same G2P natively, so no GPL dependency is pulled in. Real-device performance is also now measured (2026-09-22, via VoiceLoopLab, 5 synthesis samples during an actual conversation loop): warmup-inclusive load **0.86 s**, RTF mean **0.153** (worst 0.188), peak memory **687 MB**. RTF and warmup both clear the design doc's §04 pass bar (RTF mean < 0.2, warmup < 10s); peak memory sits between the pass line (600MB) and the concern line (900MB) — not a blocker, but worth watching. Library is confirmed as `soniqo/speech-swift`'s `KokoroTTS`. Nothing left here but building the `TtsPort` adapter for real.

- **STT finding — CORRECTED 2026-09-22: the earlier "Japan-region restriction" theory was wrong.** (If you're reading an older summary of this investigation, or a prior version of this file, distrust the region-restriction framing specifically — the rest of the debugging record below it is still accurate.)

  What's actually true: `SpeechTranscriber` (the new iOS 26 module)'s asset download — `AssetInventory.assetInstallationRequest(...).downloadAndInstall()` — does not progress for *any* locale that isn't already present on the device, not specifically English and not specifically because of region. ja-JP appeared to "work" earlier only because it was already installed at the OS level (not a real fresh download), which is what made the region theory look plausible at the time. Everything in the original debugging list (storage, Apple Intelligence enabled, restart, reinstall, reservation state, network reachability, running outside a debugger, iOS-27-SDK-vs-26.6-device gap, initializer style) is still correctly ruled out as *not* the cause — what changed is realizing the real variable was "already installed" vs. "needs a fresh download," not language or region.

  **The fix: use `DictationTranscriber` instead of `SpeechTranscriber`.** It's an older, separate module in the same `Speech` framework (same lineage as `SFSpeechRecognizer`/keyboard dictation) that can use language assets already present on the device via a different path than `SpeechTranscriber`'s broken fresh-download flow. On this test device, `SpeechTranscriber.installedLocales`/`DictationTranscriber.installedLocales` showed en-US and ja-JP already installed (almost certainly from prior real-world Siri/keyboard-dictation use) — verified two ways: (1) a self-test that fed Kokoro-synthesized English audio directly into a `DictationTranscriber` instance, which transcribed it correctly, and (2) live microphone English speech during an actual conversation, correctly recognized and logged (`認識(確定): ...`).

  **Follow-up test, 2026-09-22: `DictationTranscriber` has the identical fresh-download bug as `SpeechTranscriber`.** Requested fr-FR (confirmed absent from `DictationTranscriber.installedLocales` — only en-US and ja-JP were present) and it hung at "ダウンロード中 (0%)" exactly like `SpeechTranscriber` did for English. So the bug is general: **`AssetInventory`'s fresh-download path doesn't work on this device for *any* locale not already installed, regardless of which transcriber API requests it.** English works via `DictationTranscriber` purely because this specific device already had en-US assets from prior real-world Siri/dictation use, not because the download path itself was fixed. The root cause is still unknown (next step if it matters: the device's own system log).

  **This matters less than it sounds, because this app is for personal use on the author's own device(s), not a general product for arbitrary users.** The "won't work for a user whose device has never installed English assets" risk is real in the abstract, but irrelevant here — there is no unknown third-party user base to worry about, and English is confirmed already present and working on the actual device this runs on.

  **Decision, final: STT is `DictationTranscriber` (on-device, free), not Deepgram.** Verified end-to-end on the real device: a self-test feeding Kokoro-synthesized English audio straight into the transcriber came back correct, and live microphone English speech during an actual conversation was recognized and logged (`認識(確定): ...`) correctly. `SpeechTranscriber` remains unusable (its fresh-download path is broken); `DictationTranscriber` is the one to bridge to from Flutter. Revisit this only if the app ever needs to run on a device/account that doesn't already have English on-device assets — at that point, Deepgram (cloud, streaming) or one of `speech-swift`'s bundled on-device alternatives (WhisperASR ~1.5GB, ParakeetASR ~611MB, CanaryASR ~244MB, sidestepping `AssetInventory` entirely) are the fallbacks already scoped out for that scenario.

- **`FoundationModels` was checked too, and is fine.** This was worth checking before trusting it for phase 1's on-device summarization/correction, since it's the same Apple Intelligence family of API that `SpeechTranscriber` turned out to have a bug in. `SystemLanguageModel.default.availability` reported `.available` on this same device, and an English summarization prompt (`LanguageModelSession.respond(to:)`) completed correctly in ~3.3s (see `investigation_docs/Sources/FoundationModelsCheck.swift`, run once at VoiceLoopLab launch). No further re-verification of the other technology choices (LLM, Kokoro TTS, persistence) is warranted — whatever's wrong with `SpeechTranscriber`'s fresh-asset-download path is isolated to that one API, not Apple Intelligence broadly.

- **`investigation_docs/` (VoiceLoopLab) is a throwaway verification prototype, not the production app.** It's a standalone native Swift/SwiftUI iOS app combining design-doc implementation-order step 1 (§12: verify the voice loop alone — AEC, barge-in — **confirmed working on-device, 2026-09-21**: repeated barge-in detection during an actual conversation loop) and TTS step 3 (§09: real-device Kokoro RTF/memory/warmup — **measured 2026-09-22**: warmup-inclusive load 0.86s, RTF mean 0.153/worst 0.188, peak memory 687MB, over 5 synthesis samples during an actual conversation loop) in one place, deliberately with no real LLM dependency for its core purpose (canned replies, to keep the test deterministic — the risk being tested is the audio round-trip, not response generation). It grew a "STT 切り分け" diagnostics panel (engine picker `SpeechTranscriber`/`DictationTranscriber`, locale picker, a self-test that feeds Kokoro-synthesized audio straight to the transcriber, launch-argument-driven scripting) as part of chasing the STT finding above — that panel is what confirmed both the `DictationTranscriber` workaround and the fr-FR fresh-install failure. Its purpose is to de-risk before writing the real Flutter app's native modules; what gets carried forward is the *findings* (AEC works via `.playAndRecord`+`.voiceChat`+voice processing, the barge-in RMS-threshold approach, Kokoro's real-device behavior, the STT approach once finalized) into the production `sessionMachine` and the Flutter↔Swift platform-channel bridges — not the prototype's code itself.

- **Backend: none.** This is a deliberate, load-bearing decision in the design doc (a serverless hybrid), not a gap to fill in — don't add one for the English-learning feature. A backend only reappears in a possible future phase 2, as an MCP server for IoT/agent tool integrations (design doc §10), and even then the English-conversation path stays backend-free.

- **Phase 2 (agent/IoT, design doc §10–11):** adds a Dialog Orchestrator (`ConversationPolicy` vs. `AgentPolicy`) and a Tool Registry (HomeKit/Matter, App Intents, an MCP client) behind the *same* `ConversationSessionPort` — the audio layer doesn't change. Conversation mode and device-control mode must stay hard-separated (empty `tools` list in conversation mode, switched only by explicit UI/wake-word, never inferred) so saying "turn off the light" while practicing English can't trigger a real action. Three cheap preparations to make now, while still in phase 1, per §11 (skip everything else — no Tool Registry or Orchestrator yet, that would be premature): domain type names stay generic (`Turn`/`Session`, done above), `LlmPort` already carries `tools`, and the persistence schema should get a nullable `tool_calls` column from the start.
