01

設計の3原則

個別の技術選定はすべてこの3つから導かれている。判断に迷ったときはここに戻る。

1. ホットパスとコールドパスを分ける

会話中（ホットパス）はレイテンシ最優先で、余計な処理を一切挟まない。発音・文法フィードバックのような分析処理は、会話終了後（コールドパス）に非同期でまとめて実行する。ユーザーは会話が終わってから結果を見るため、体験を落とさずにコストと遅延を切り離せる。

2. 課金が発生しない処理はすべてローカルへ寄せる

iPhone 16e は Apple Intelligence 対応端末であり、FoundationModels（約3B のオンデバイス LLM）が無料で使える。品質が体験に直結する箇所（会話生成・音声合成）だけをクラウドに残し、それ以外はローカルに置く。STT も DictationTranscriber によりこのローカル・無料側に残った（§13）。

3. 差し替え点を1箇所に集約する

「カスケード構成」と「Speech-to-Speech 構成」は、外から見れば同じ責務を果たす。両者を ConversationSessionPort という単一のインターフェースの裏に隠し、アプリ層が実装を知らない状態を保つ。フェーズ2 のエージェント化もこの境界の上に載る。

併せて、プロバイダ側で月額上限を設定し、このアプリ専用のキーを発行しておくこと（revoke が他に影響しない）。

レイテンシとコスト

応答レイテンシの内訳

1発話終了検知 → 確定テキスト LOCAL0.1–0.2 s
2LLM 1文目の生成完了 CLOUD0.4 – 0.7 s

区間1は DictationTranscriber（オンデバイス）採用確定により、ネットワーク往復なしで元の見積もり通り（§13）。

Speech-to-Speech 構成の約 0.5 秒には及ばないが、英会話学習という用途ではむしろ許容範囲。ネイティブ同士の会話より一拍空く程度で、学習者が聞き取って考える間として自然に働く。

なお フェーズ1.5 で TTS をオンデバイス化すると区間3のネットワーク往復が消え、合計 0.5–1.0 sまで縮む見込み。

実装上の必須テクニック

LLM の出力を文単位で切って逐次 TTS に流すこと。全文の生成を待たずに1文目から再生を始めれば、体感レイテンシはおよそ半分になる。これをやらないと 3 秒級まで悪化する。

05

コード構成

DDD の戦術パターンは採用せず、依存を内向きにするという原則だけを借用する（ポート&アダプタ）。このアプリの複雑さは業務ルールではなく I/O のオーケストレーションと状態遷移にあるため。

    conversation.ts                # Session / Turn / Message
    contextPolicy.ts               # 直近N往復 + 要約 の組み立て
    sessionMachine.ts              # 会話ループの状態機械

  ports/                           # interface のみ
    ConversationSessionPort.ts     # ★唯一の差し替え点
    SttPort.ts  LlmPort.ts  TtsPort.ts
    SummarizerPort.ts
    ConversationRepository.ts

  adapters/
    session/
      CascadeSession.ts            # Stt+Llm+Tts を合成（フェーズ1採用）
      RealtimeSession.ts           # Speech-to-Speech 直結（将来の差し替え先）
    stt/DictationTranscriberStt.ts # ← Swift ブリッジ、採用確定（§13）
    summarizer/FoundationModelsSummarizer.ts  # ← Swift ブリッジ
    llm/OpenAiLlm.ts
    tts/StreamingTts.ts
    repo/SqliteConversationRepository.ts

  app/                             # hooks / 画面

domain/ が Node 上だけで完結してテストできることが重要。コンテキスト圧縮ロジックを実機なしで検証できる効果は、地味だが開発速度に大きく効く。

意図的に採用しないもの

  • 集約ルート・不変条件の強制 — 守るべき不変条件がほぼ存在しない
  • Domain Event / イベントソーシング — 過剰
  • 層ごとの DTO とマッパー — 1人開発では変換コードが増えるだけ
  • ユビキタス言語のドキュメント化 — 共有する相手がいない
  • Repository の過剰抽象化 — SQLite 1つなので薄い interface で足りる
06

主要インターフェース

ConversationSessionPort

Speech-to-Speech は STT・LLM・TTS が1つに融合しているため、3ポートに分割した設計では Realtime API へ差し替えられない。そこで上位に1枚かぶせ、実装側で合成するか直結するかを選べるようにする。

interface ConversationSessionPort {
  start(config: SessionConfig): Promise<void>
  sendAudio(chunk: Int16Array): void
  interrupt(): void                        // barge-in
  onTranscript: (t: Transcript) => void    // 学習ログ用に必ず取る
  onAudioChunk: (a: AudioChunk) => void
  close(): Promise<void>
}

実装は2通り。上位から見れば同一なので、切り替えてもアプリ層は一行も変わらない。

  • CascadeSession — 内部で SttPort / LlmPort / TtsPort を合成 フェーズ1採用
  • RealtimeSession — Speech-to-Speech API に直結 将来の差し替え先

LlmPort — tools を最初から生やす

フェーズ1 では常に空配列を渡すが、引数だけは最初から定義しておく。ストリーミング実装に後からツール呼び出しを差し込むのは想像以上に面倒で、フェーズ2 の着手コストを大きく左右する。

interface LlmPort {
  stream(req: {
    messages: Message[]
    tools: ToolSchema[]      // フェーズ1では常に [] を渡す
    signal: AbortSignal
  }): AsyncIterable<LlmDelta>
}
07

会話ループの状態機械

バグの大半はここに集中する。割り込み、ネットワーク断、TTS 再生中の新規発話、バックグラウンド遷移。これらを boolean フラグの組み合わせで捌くと確実に破綻するため、XState か手書き reducer で明示的にモデリングする。

フェーズ2 で追加される遷移
最初に潰すべき技術リスク

エコーキャンセル。TTS 再生中もマイクを開けておかないと barge-in が実装できないが、素朴に作るとスピーカーの音を自分で拾って STT が誤作動する。

AVAudioSession を .playAndRecord + .voiceChat モードに設定すると OS の AEC が有効になる。ここを通さないまま先に進むと、後で全面的な作り直しになる。プロトタイプの一発目でこの音声ループだけを単独検証すること。

08

コンテキスト管理

長い会話でコストが膨らむ最大の原因は、毎ターン全履歴を再送すること。DB には生ログを全件残しつつ、LLM に渡すのは以下の3層だけに絞る。

層内容生成
1. 直近ターン直近 8〜10 往復を生のまま—
2. セッション要約一定ターンごとに圧縮し、古い生ログをコンテキストから外すFoundationModels
3. ユーザープロフィールレベル、苦手な文法、頻出の誤り。システムプロンプトへ注入FoundationModels

2 と 3 の生成をローカルモデルに任せられるため、圧縮処理そのものは無料になる。運用面では 1 セッションを 15 分程度で区切るのも有効。

09

フェーズ1.5：TTS のオンデバイス化

クラウド TTS を OSS の軽量モデルに差し替える検証フェーズ。目的はコスト削減ではなくレイテンシとオフライン動作。TtsPort の裏を入れ替えるだけで、アプリ層も CascadeSession も変更しない。

Status — 2026-09-15

試聴テスト（検証ステップ1）合格。Kokoro-82M の採用を方針として確定。 全10項目のチェックリストを通過し、発音の手本として許容できると判断した。G2P の懸念も MisakiSwift により解消済み。

残るは実機での性能実測（ステップ3）とライブラリ選定のみ。ここで RTF・メモリ・ウォームアップ時間が想定内であれば、そのまま TtsPort アダプタの実装に進む。

観点変化評価
体感レイテンシ1.0–1.5 s → 0.7–1.0 s本命。ネットワーク往復 0.3–0.5 秒が丸ごと消える
オフライン動作不可 → 完全対応会話全体がオフラインで成立する
ランニングコスト$6/月 → $0これだけが理由なら見送るべき水準
アプリサイズ+80 – 170 MBCore ML + INT8 量子化なら ~80 MB。許容範囲
音声品質要 A/B 試聴クラウド最上位には未達。特に抑揚と間

候補：Kokoro-82M

Apache 2.0、82M パラメータ。この規模で TTS Arena 上位の品質に達しており、Core ML / MLX への移植版が複数公開されている（kokoro-ios / kokoro-coreml / mlx-audio）。gapless streaming に対応しているため、文単位の逐次再生にもそのまま乗る。

性能は iPhone 16 Pro で RTF 0.08（1秒の音声を 0.08 秒で生成）という報告があり、A18 搭載の 16e でも実用域に入る見込み。

ベンチマークの食い違いに注意

別の比較では Kokoro は「FTTS 3,658 ms / ピークメモリ 2.0 GB / デスクトップ・サーバー向き」と評価されている。これはおそらく PyTorch 実装のデスクトップ計測であり、Core ML 版の iPhone 実測とは別物。採否は自分の実機での実測で判断すること、公開ベンチを鵜呑みにしない。

G2P 依存：調査済み・解決済み

Resolved — 2026-09 調査

当初この設計の最大リスクと見ていた espeak-ng（C ライブラリ・GPLv3）の iOS ビルドは不要だった。Kokoro 公式 G2P である misaki の Swift 完全移植 MisakiSwift（Apache-2.0） が公開されており、辞書 + 接尾辞処理 + BART ニューラルフォールバックの3層構成をネイティブで提供している。kokoro-ios は Package.swift で espeak-ng 依存を明示的にコメントアウトし、MisakiSwift を既定の G2P としている。

結果として GPLv3 の伝播も起きないため、配布形態の制約を考慮する必要がなくなった。

残る留意点

  • ストリーミング API はない — Kokoro は非自己回帰モデルで一括合成。ただし現行設計はもともと文単位で TTS に流す方式なので、チャンク運用でそのまま噛み合う。設計変更は不要
  • ウォームアップ — 初回推論が遅い。セッション開始時にプリロードする
  • トークン長上限 — kokoro-ios は 510 トークン。文分割はアプリ側の責務（既存設計と整合）
  • 発熱・バッテリーは RTF 0.08 なら実質問題にならない

ファインチューニングは当面不要

TTS の学習が必要になるのは「特定の話者の声を再現したい」ときに限られる。本件の要件は「英語として自然な発音の手本」であって声の同一性ではないため、事前学習済みモデルをそのまま使う。

学習にはクリーンなスタジオ品質の音声が数時間分必要で、データ整備と試行錯誤で数週間かかるうえ、元の事前学習モデルより品質が下がるリスクのほうが高い。実施するとしても、声の同一性という要件が明確に立ってから（実行環境は Google Colab を想定）。

検証手順

  1. 試聴による採否判定 — 合格（2026-09-15）Colab ノートブックでボイス選定 → プロソディ耐久テスト（疑問文の上昇調・縮約形・対比強勢・最小対立ペア等）→ 速度変更 → 会話ターン再現 → A/B の10項目を実施し、全項目を通過。発音の手本として許容できると判断。
  2. G2P 依存の解決方法を確認 — 完了MisakiSwift（Apache-2.0）により解決済み。espeak-ng は不要で、GPLv3 の制約も発生しない。上記参照。
  3. iPhone 16e 実機で RTF・メモリ・ウォームアップを実測公開ベンチに食い違いがあるため必須（Colab の計測値は x86 CPU のもので実機性能を示さない）。ウォームアップ後の定常値と初回レイテンシの両方を計測する。
  4. TtsPort アダプタとして実装採用が決まってから着手。第1候補は soniqo/speech-swift の KokoroTTS。差し替えのみで完結するはずで、他の層に波及したら設計ミスを疑う。
判定基準（試聴チェックリストの要点）

一般的な TTS 評価とは基準が異なる。「聞き取りやすいか」ではなく「真似してよい発音か」で判断する。自然さがやや劣るのは許容できるが、次の4点は許容できない — 母音・子音の音価のずれ、単語の強勢位置の誤り、疑問文が上昇調にならない、意味の切れ目と無関係な区切り。

実施タイミング

フェーズ1 では着手しない。 実装順序のステップ1（音声ループ単体の検証）が通ってから取りかかる。ポート設計を入れておいたおかげで、後回しにしても手戻りが発生しない構造になっている。

MCP Client任意の外部ツール

ツール層は MCP で話させる

ツールを増やすたびにアプリを再ビルドする運用は続かない。ツール側を MCP サーバーとして外に出し、アプリを MCP クライアントにすることで、ツール追加とアプリ改修を切り離す。この段階で初めてバックエンド（自宅の小型サーバー等）が必要になるが、用途が明確なので健全な追加といえる。英会話のためのサーバーは最後まで不要のまま。

ローカルモデルによるインテント振り分け

FoundationModels はツール呼び出しに対応しているため、フェーズ1 で入れた仕組みがそのまま活きる。

  • 「会話か、デバイス操作か」の判定 → ローカル・無料・即時
  • 「電気を消して」レベルの単純命令 → ローカルで完結。クラウド不要、オフラインでも動作
  • 複雑な多段タスクのみ → クラウドのエージェントへエスカレーション

照明の ON/OFF のためにクラウドへ往復して課金するのは不合理なので、この振り分けは実用上かなり効く。

会話モードと操作モードは必ず分離する

安全性と学習体験の両面から必須

英会話の練習中に "Could you turn off the light?" と発話したら実際に消灯した、という事態を防ぐ。英会話モードでは tools に空配列を渡し、物理的に呼べない状態にする。モード切替はウェイクワードか明示的な UI で行い、暗黙の自動判定に頼らないこと。

副作用を持つ操作で追加される考慮点

  • 確認フロー — 不可逆な操作（施錠解除・送信・購入）は音声での明示確認を挟む
  • 冪等性 — 音声認識の揺れで同一命令が二重に飛ぶ。リクエストに ID を振って重複実行を防ぐ
  • プロンプトインジェクション — エージェントがメールや Web を読むようになったら、その内容は命令ではなくデータとして扱う。読み込んだ内容に含まれる指示でツールを実行させない。後付けが難しいため、Orchestrator の設計時点で構造に組み込むこと
11

いま打っておく布石

フェーズ2 のためにいま作るべきものは何もない（YAGNI）。ただし後から入れると高くつくものが3つだけある。これらは今のうちに済ませておく。

  1. domain/ を英会話に固有の名前にしない LessonTurn ではなく Turn、Lesson ではなく Session。エージェント化の際、ドメイン層全体のリネームは非常に高くつく。
  2. LlmPort に tools 引数を最初から生やす 当面は空配列を渡すだけでよい。ストリーミング実装に後からツール呼び出しを差し込む作業は、想像以上に広範囲へ波及する。
  3. SQLite スキーマに tool_calls を nullable で先に入れる マイグレーションは後回しにするほど痛みが増す。カラム1本の先行投資で済む。

逆に、Tool Registry も MCP クライアントも Orchestrator の分岐も、いまは作らない。上記3点だけで拡張の扉は開いたままになる。

実装順序

技術リスクの高い順に並べてある。特に 1 は、失敗した場合に構成全体の見直しが必要になるため最優先で検証する。

  1. 音声ループ単体の検証 — 完了（2026-09-21, VoiceLoopLab）AVAudioSession の AEC 設定、録音 → 再生 → barge-in。実機（iPhone 16e / iOS 26.6）で会話ループ・barge-in 検出が連続で動作することを確認済み。最大の技術リスクだったが解消。
  2. STT 接続（採用確定、§13参照）当初想定の SpeechTranscriber Swift ブリッジは新規ロケールの資産ダウンロードが進まない不具合あり。DictationTranscriber（同じくSwiftブリッジ、オンデバイス）に切り替えて実機確認済み。未インストール言語の新規取得は同じ不具合で通らないと判明したが、個人利用限定というスコープではこの制約は問題にならないため採用を確定。
  3. CascadeSession の実装クラウド LLM + TTS を接続。文単位で TTS へ流す逐次再生をここで作り込む。
  4. sessionMachine と SQLite 永続化状態遷移を明示化し、transcript を tool_calls 列込みのスキーマで保存。
  5. FoundationModels ブリッジ + コンテキスト圧縮要約生成をローカルに寄せる。contextPolicy は Node 上で単体テストしてから繋ぐ。
  6. 復習・フィードバック画面コールドパス。会話終了後にローカルで添削を生成して表示。
  7. フェーズ1.5：TTS のオンデバイス化検証Kokoro-82M の試聴 → G2P 依存の確認 → 実機で RTF 実測 → A/B 判定。詳細は §09。TtsPort の差し替えのみで完結する。
  8. （必要なら）RealtimeSession への差し替えレイテンシが体験上のボトルネックと判断された場合のみ。アプリ層の変更は不要。
13

不採用とした選択肢

検討の過程で外した案と、その理由。同じ議論を繰り返さないための記録。

SpeechTranscriber（新STT、オンデバイス）不可（新規ロケールの資産DLが進まない）

§03 で当初採用していたが、VoiceLoopLab による実機検証（iPhone 16e / iOS 26.6）で、AssetInventory.assetInstallationRequest → downloadAndInstall() が無期限にハングすることを確認した。

2026-09-21 時点の結論（誤り、下記参照）: 英語（en-US・en-GB）だけ再現し日本語（ja-JP）は問題なく完了したため、日本リージョンでの英語オンデバイス音声認識アセットの提供制限が原因と判断した。切り分けのために確認・除外した要因: ストレージ容量、Apple Intelligence の有効化、端末再起動、AssetInventory の予約状態、ネットワーク到達性、デバッガ経由の起動、SDK/OS バージョンの差異（iOS 27 SDK でビルド・iOS 26.6 実機）、言語設定（英語は「使用する言語」に登録済み）、実装の書き方（公式サンプル SpeechAnalyzerSample と同一の初期化オプションに変更しても再現）。

2026-09-22 訂正: 地域制限ではなかった。SpeechTranscriber.installedLocales を確認すると、ja-JP は既にこの端末にインストール済みだった——「動いた」のは新規ダウンロードではなく、単に不要だっただけ。実際に起きているのは「端末に未インストールのロケールでは、言語を問わず資産ダウンロードが進まない」という不具合で、英語固有でも地域固有でもない。OS側でなぜ止まるのかは依然不明（次に調べるなら端末のシステムログ）。

なお、この制限は Apple Intelligence 全体ではなく SpeechTranscriber のこの経路に固有と確認済み。同じ Apple Intelligence 系 API である FoundationModels を同一端末で英語テキストに対して試したところ、availability: available・英語での要約生成とも正常に完了しており、他の技術選定（LLM・Kokoro TTS・FoundationModels・永続化）を見直す必要はない。

DictationTranscriber（旧STT系統、オンデバイス）採用確定

同じ Speech フレームワーク内にある別モジュールで、キーボード音声入力・旧 SFSpeechRecognizer と同系統の資産を使う。この端末では en-US・ja-JP とも既にインストール済みで、SpeechTranscriber の壊れたダウンロード経路を経由せずに使える。

実機で確認済み（2026-09-22）: (1) Kokoro で合成した英語音声を直接流し込む自己診断テストで、入力文とほぼ一致する文字起こしを取得。(2) 実際にマイクへ英語で話しかけ、会話中に正しく認識・確定（ログに 認識(確定): ... として記録）。

追試で判明した既知の制約（受容済み）: 端末に一度も入っていない言語を、DictationTranscriber が新規にダウンロードできるかを fr-FR（この端末に未インストールのロケール）で追試したところ、SpeechTranscriber と同じ「新規ダウンロードが進まない」不具合を確認した。一般ユーザー向けアプリなら「英語を一度も使ったことがない端末では動かない」という本番導入不可のバグになるところだが、本アプリは個人利用限定であり、使用する端末（この iPhone）には英語アセットが既にインストール済みであることを確認しているため、この制約は実運用上の問題にならない。

判定・最終: 採用確定（オンデバイス・無料）。Deepgram（クラウド・ストリーミング）は個人利用では不要と判断し導入しない（§03参照）。もし将来、英語アセット未インストールの端末で動かす必要が生じた場合は、Deepgram、または speech-swift パッケージが同梱する完全オンデバイスの Whisper / Parakeet / Canary 等（244MB〜1.5GB）が代替として選定済みのフォールバックになる。

Speech-to-Speech API 直結保留・差し替え可

レイテンシは約 0.5 秒と優秀だが、月額が $25–60 とコスト要件に合わない。ただし ConversationSessionPort の実装を1つ足すだけで移行できる状態を維持する。

Claude Pro サブスクリプションのバックエンド転用不可

3つの理由で成立しない。(1) Free/Pro/Max のクレデンシャル経由でアプリのリクエストをルーティングすることは規約で明確に禁止されている。(2) リアルタイム音声 API が存在せず、本件の中核を担えない。(3) 5時間セッション制限と週次制限があり、上限に達したら待つしかない。本番用途は Console の API キー（Commercial Terms）を使う、というのが提供側の明示的な線引き。

完全オンデバイス構成（Apple 標準 API のみ）一部見直し

AVSpeechSynthesizer の音声品質が機械的すぎるため、発音の手本としては不適。約3B の FoundationModels も指示追従が弱く、レベル調整や自然な言い直しが安定しない。ただしこの判断は Apple 標準 API を前提としたもので、OSS の Kokoro-82M は明確に一段上の品質にある。TTS のみ フェーズ1.5 でローカル化を再検証する。応答生成のローカル化は引き続き不可。

ExecuTorch / llama.rn による大きめのローカルモデル同梱不可

Gemma 3n や Qwen3 4B クラスも動作するが、アプリに 2–4GB のモデルを同梱することになり、発熱とバッテリー消費も現実的な問題になる。個人利用の1アプリが背負うには重い。なお TTS（82M・数百MB）はこれとは桁が違うため、別途 §09 で検証する。

TTS モデルの自前ファインチューニング当面不要

学習が必要になるのは「特定の話者の声を再現したい」場合に限られる。本件の要件は発音の手本であって声の同一性ではないため、事前学習済みモデルをそのまま使う。クリーンな音声が数時間分必要で数週間かかるうえ、元モデルより品質が下がるリスクのほうが高い。要件が立った時点で Google Colab 上で実施を再検討する。

API Gateway / BaaS バックエンド不要

当初の設置目的は「APIキーの秘匿」と「音声パイプラインの実行」だった。個人利用でキーを SecureStore に置く方針と、STT がローカルに移ったことで、どちらの理由も消滅した。フェーズ2 の MCP サーバーとして別途復活する。

DDD の戦術パターン一式過剰

DDD が真価を発揮するのは複雑な業務ルールと不変条件がある場合。本アプリの難所は I/O オーケストレーションと状態遷移であり、集約ルートや Domain Event を持ち込む対象がない。依存を内向きにする原則だけを採用し、戦術パターンは捨てるのがこの規模の最適解。

APIキーのバンドル埋め込み（.env / EXPO_PUBLIC_*）不可

React Native はビルド時に JS バンドルへ値を埋め込むため、ハードコードと実質同じ。初回起動時に手入力し expo-secure-store（Keychain）へ格納する方式を採用。
